# Hardening notes: volgenic/vault, run 1

Defence-in-depth notes the hunters recorded beside their coverage units. None of these is a finding: each one either crosses no trust boundary (most need a same-UID process, which the vault's accepted design already trusts), or needs conditions the source can't show. Verdicts and severities are only in `findings.json`. Each note is quoted from the hunter that wrote it; line numbers are at commit 9b36136.

Notes that duplicate a candidate were folded into it:

- hunter-stream: see the record `rules.rs/check_caller_headers/method-and-path-override-headers-not-refused`.
- hunter-stream: see the record `src/server.rs:stream:caller-induced-401-marks-login-refused`.
- hunter2-lifecycle: see the record `src/server.rs:stream:caller-induced-401-marks-login-refused`.

## Fixed in this pull request

- **hunter-leak**: src/store.rs:279 and src/backup.rs:164-166 build the whole plaintext vault document with serde_json::to_vec, which starts small and grows by reallocation; Zeroizing wipes only the final buffer, so each save and backup leaves freed heap fragments holding every secret (as decimal byte arrays). backup::plaintext_size already counts the exact size with a ByteCounter: pre-size a Zeroizing Vec with that count and use serde_json::to_writer, as client::call_secret does. *(Fixed by H-03.)*
- **hunter-leak**: src/client.rs:130 pre-sizes the outgoing secret request at 128 KiB, but secret_bytes serializes a value as a JSON number array (up to 4 bytes per byte), so a value over about 32 KiB reallocates and leaves an unwiped copy in the CLI's freed heap; size it from value.len()*4 plus overhead. *(Fixed by H-03.)*
- **hunter2-mirror**: MirrorReport sanitizes 'detail' for control characters but stores newest_file with only a 300-char cap (src/server.rs:834-838). It is not printed by the text status today; if a later display prints it, apply the same control-character filter. *(Fixed by H-02.)*

## Secrets in memory

- **hunter-proto**: src/model.rs:533-535 with src/protocol.rs:401-405: secret_bytes::deserialize uses deserialize_bytes; for a JSON string value containing an escape, serde_json unescapes it into its own scratch Vec, which is not wiped, so a typed value or recovery key sent as an escaped string leaves an unwiped copy in freed memory, contrary to the parse_request comment (R1). The command-line tool sends a byte array (serialize_bytes), which takes the wiping visit_seq path, so only non-CLI callers are affected; reading the residue needs memory access that harden_process denies. Accepting only the array form, or documenting the string form as unwiped, would close the gap. *(Same as a note from hunter-leak (serde_json's escape scratch for intake values).)*
- **hunter-leak**: src/main.rs:292-295 reads a stdin value with read_to_string into a growing String and then trim_end_matches(..).to_string() makes a second unwiped-on-drop copy before from_string; only the first String is zeroized, and its earlier reallocations are not. Read into a WipingBuf instead.
- **hunter-leak**: SecretValue::lock/Drop (src/secret.rs:101-109, 155-163) call mlock/munlock per allocation, but page locks don't nest: dropping one SecretValue munlocks the whole page, unlocking any other live SecretValue sharing it. On Linux with unencrypted swap a live secret can then be paged out. Either mlock nothing (as macOS's comment already assumes encrypted swap) or allocate secrets from a dedicated locked arena.
- **hunter-leak**: HeaderValue::from_bytes (src/proxy.rs:144, src/stream.rs:486) copies the credential into a non-zeroized Bytes buffer, and hyper's request encoder copies it again; set_sensitive only hides it from Debug. This is inherent to reqwest and worth naming in R1's list of unavoidable copies.

## The socket daemon's availability (same-UID callers)

- **hunter-proto**: src/server.rs:411 and 222-251: the 10-second read timeout applies per read(), not to the whole request line, so a caller that sends one byte every few seconds can hold a connection slot for weeks; 128 such callers hold every slot and every other caller gets busy. Only a same-UID caller can do this (and it can already kill the daemon), so this is hardening: give read_request_line an overall deadline (for example 10 s from accept, checked against an Instant before each read).
- **hunter-proto**: src/server.rs:269: read_payload resizes the buffer to the declared length (up to 32 MiB, zero-filled, so committed) before any byte of the payload arrives; 128 connections declaring body_len 33554432 commit about 4 GiB. Same-UID only; reading in chunks into a growing buffer would make memory follow bytes actually received.
- **hunter-proto**: src/server.rs:201-202: an accept() error is skipped with continue and no back-off, so under EMFILE (macOS LaunchAgents default to a 256 soft file limit; 128 callers plus their upstream sockets approach it) the accept loop spins at full CPU until descriptors free up. A short sleep on error, or raising RLIMIT_NOFILE at start, would bound it.

## Install, platform and the vault key

- **hunter-ipc**: src/install.rs:68-74 ensure_dir calls create_dir_all with the process umask and then chmods 0700, and follows a symlink in both steps. Create the folder with DirBuilder::mode(0o700) and verify it with store::check_dir (lstat, owner, no 077 bits) as the daemon does. That closes the short window in which a new folder has the default mode, and stops a planted symlink from being chmodded and used.
- **hunter-ipc**: src/install.rs:82-96 install_program reads the executable by its path twice (once to compare, once to copy) after it has started. Read it once from one opened descriptor (or /proc/self/exe on Linux) so the bytes installed are the bytes compared and running.
- **hunter-ipc**: src/server.rs:107-109 the daemon runs check_dir on the vault, backups and socket folders but not on base, bin/ (which holds the program the service runs) or the log folder. Adding them would catch a folder whose mode was loosened after install.
- **hunter-ipc**: src/platform.rs:82-92 SO_PEERCRED reports the peer's UID as seen from the daemon's user namespace. A rootless container whose root maps to the owner's UID and has the socket bind-mounted would pass the check. Whether containers can reach the socket at all is up to the host (README says they cannot), so this is a deployment note, not a finding. *(Needs a check on the other side (host: how containers reach the socket).)*
- **hunter-store**: keyprotect::load falls back to the plain vault.key when unsealing the TPM credential fails and both files exist (an interrupted seal). Status reports it, but a disk copy taken in that state opens the vault anywhere. Finishing or retrying the seal at daemon start would shorten that window.

## Store, backups, mirror and the audit chain

- **hunter2-mirror**: Backup selection is lexical on the file name: generations are formatted {:06} (src/backup.rs:124, 184) and list() sorts PathBufs bytewise (src/backup.rs:295). Past generation 999999 a 7-digit name sorts before 999999, so latest() returns an old file and prune() (src/backup.rs:343-350) deletes the newest backups. Every commit and renew raises the generation (src/vault.rs:297, 912), so this is reachable only after a million changes. Fix: sort by the parsed generation_of() value, or zero-pad to 20 digits. *(Also reported by hunter-store.)*
- **hunter2-mirror**: mirror_once prunes and picks 'newest' in the synced mirror folder by name alone (src/mirror.rs:56-57). Files with this vault's prefix and a higher generation, written into iCloud Drive by another device on the same account, would outrank the real copies: the mirror would delete each real backup right after copying it and still report ok. Anyone who can write the synced folder can already delete files there, and the report is stated as unverified. Hardening: prune the mirror only among names that match files the mirror copied from the local folder, or use the local folder's generation set.
- **hunter-store**: Rollback of vault.bin is not detected. The vault key never rotates and the AAD (magic+id) carries no generation, so an older vault.bin decrypts. audit::check accepts any earlier head still in the chain, and needs_backup passes because that generation's backup matches. The next commit then finds the existing future backup for N+1, fails with BackupMismatch, and ready_for_change refuses all later changes. Only a same-UID writer can do this. Checking doc.generation against the newest local backup's generation at open would turn this into a clear alarm.
- **hunter-store**: vault::restore (src/vault.rs restore) accepts any backup whose payload.recovery_recipient matches the typed identity, and it does not bind to the recovery recipient of the restore point that `vault reset` left. It also does not re-validate restored records (validate_name, rule parse, caps.validate, kind/field consistency). While no vault is open (after reset, or after `install --for-restore`), a same-UID process can install a vault under its own recovery key first. Binding a file restore to the recipient recorded beside the restore point, and re-running record validation on restore, would close this. It is not a finding because the attacker is same-UID.
- **hunter-store**: Audit chain (src/audit.rs): with an unkeyed chain and the head saved only at changes, a same-UID writer can drop use lines written after the last change without detection. The incremental check() also only reads past the checkpoint offset of the current audit.log, so an in-place edit of an already-checked line shows up only at the next daemon start or `vault audit --all`. Both are within the accepted same-UID trade-off. Recording a periodic head, or stamping the current file's checked prefix, would narrow them.

## Proxy, stream and renewal

- **hunter-proxy**: Echo scrub matches only whole, aligned forms of the key (scrub.rs:13-37). A caller may send Range (accepted by check_caller_headers, shown in the probe), so an upstream echo endpoint that honors Range on dynamic responses would return key slices the scrub cannot see; also base64 of a larger blob in which the key is not 3-byte aligned (e.g. base64 of 'Bearer <key>', prefix 7 bytes) and JSON-escaped forms ('\/', '\u00xx') are not matched. Consider refusing range/if-range in REFUSED_HEADERS and adding needles for the full header value (prefix+key+suffix) in its base64 forms at the three alignments.
- **hunter-proxy**: A reply whose bytes are compressed without a Content-Encoding header (e.g. Transfer-Encoding: gzip, chunked, or a gzip content type) bypasses the scrub's view; only reachable if the upstream compresses unasked, since te and accept-encoding are refused.
- **hunter-proxy**: A very short stored key (1-2 bytes) makes nearly every reply echo_blocked; parse/add could set a minimum key length (availability only, same principal).
- **hunter-stream**: src/logins.rs line 615 computes now + expires_in as u64 with unchecked addition; a token-server reply with a huge expires_in saturates the cast to u64::MAX and the addition overflows (abort in a dev build with panic = abort, wrap in release). The token server is a fixed TLS host, so a socket caller cannot reach it; use saturating_add and cap the expiry.
- **hunter2-lifecycle**: src/vault.rs:898-906 / src/server.rs:1349: the renewal compare-and-set uses record.version, which rename (vault.rs:1105) also raises without changing the value. A rename that lands while a refresh call is in flight makes Vault::renew return VersionMismatch, and the server drops the renewed tokens silently (no log, no audit line), although source says the provider has already retired the old refresh token. The login is then lost at its next renewal. Locally observed (artifact out.txt). Only same-UID callers can rename, and they can already delete, so no boundary is crossed. Fix: compare a value digest (or a separate value_version) instead of version, or take the per-login renewing lock in rename. At minimum, audit and log the dropped renewal.

## Wallets

- **hunter-wallet**: Ethereum signatures never expire, so the rolling 24-hour caps bound how fast the vault signs, not how fast payments land: a relay or agent that holds each day's signed payments at consecutive nonces can broadcast several days' worth at once, and check_cancel (src/wallet.rs:1143-1156) only cancels a nonce signed for in the last 24 hours, so a held payment older than that can be voided only by signing a new payment at its nonce. README.md:559-560 says the caps 'never under-count one that landed', which holds per signing time only. Consider stating this in the README's Wallets section, or letting the owner cancel at any nonce the wallet has ever signed for.
- **hunter-wallet**: Test-network wallets (solana_devnet, tron_nile) put no network identifier into the signed bytes, because Solana and Tron have none. The network is chosen only by the recent blockhash or ref block the caller supplies, so a caller that gives a mainnet blockhash gets a dry-run wallet's transfer that is valid on mainnet (src/wallet.rs:813, 836-838). This matters only if the dry-run address also holds mainnet funds. Consider documenting that a test wallet's address must never be funded on mainnet.
- **hunter-wallet**: While the Recovery Kit file stays at ~/Volgenic Vault Recovery Kit.txt (0600, README.md:43; confirm-kit is optional), any process running as the owner's user can read the recovery key that guards wallet-create and wallet-caps (src/vault.rs:575-585). This is the accepted same-UID trade-off, the same exposure as the vault key file. Consider making the CLI's wallet create step urge confirm-kit.

## Intake, lease and fill

- **hunter-intake**: R40 refuses a sealed app_secret replace so that a build never runs with the sealer's value. A sealed app_secret can still be added, leasable, under any name the vault does not hold. That includes a name a lease reports as missing, and the gap during the documented change procedure 'delete, then add' (README.md:411-412). In those cases the build gets the sealer's value, so the threat model's claim 'can't change the value a build gets' holds only for names already held. This falls under the accepted 'seal one of its own' risk (src/intake.rs:29-31). Consider making a sealed leasable add need owner confirmation, or having the host refuse a lease of a name it did not see the owner add.
- **hunter-intake**: lease::choose (src/lease.rs:130-153) matches by name or id only and never compares the record's app with the job's application. Any leasable app secret can be leased to any job, so the per-application tag is advisory.
- **hunter-intake**: Since fill's origin is caller-asserted (README.md:319-324), any same-UID process can read a login password by naming an origin on its site. The current design page's 2026-11-17 block describes an engine:"app" caller-signature check (platform::peer_is_volgenic_app). That check is absent from this tree (proposed in vault PR 24, not merged), and the README's accepted gap stands until it lands. *(Needs a check on the other side (host and app: who may call fill).)*
- **hunter-intake**: A sealed replace of a fixed-host kind takes site from the sealed object without semantic validation (src/server.rs:545-549). It cannot redirect traffic, because kinds fix the hosts, but it can set a misleading site label shown by list.

## The command-line display

- **hunter2-cli**: src/main.rs list/health/restore print names, sites, apps and usernames with plain {}; these are validated on store (src/model.rs:462-501) so they are safe today, but escaping at the CLI renderer would make every display path independent of daemon-side validation.
- **hunter2-cli**: src/main.rs delete confirms by name only and sends SecretRef::Name; delete is open to every caller without the recovery key, so a rename swap grants nothing new, but sending the listed id would make the prompt bind to what it names.
- **hunter2-cli**: status prints mirror.at and mirror.detail from the mirror report; detail is control-filtered (src/server.rs:832) and the CLI already labels it as reportable by any program running as the owner.

## Release and supply chain

- **hunter-supply**: Release binaries embed the builder's absolute CARGO_HOME in panic-location strings: a local cargo build --release --locked held 305 strings like /home/node/.cargo/registry/src/index.crates.io-.../tokio-1.54.1/... (agents/hunter-supply/artifacts/out.txt). A release built on the owner's machine would carry e.g. /Users/<account>/.cargo/..., which undercuts release.sh:74-75's stated aim that the archive 'names no local account'. Low impact (an account name). Fix: in release.sh, export RUSTFLAGS="--remap-path-prefix=$HOME=~" (or CARGO_HOME), or set [profile.release] trim-paths once stable.
- **hunter-supply**: scripts/release.sh --add (lines 105-120) does not check that HEAD equals the release's target commit, and with TARGETS unset on a Mac (line 40) it rebuilds the Linux archives with zigbuild and uploads them with --clobber over the published ones. A volgenic/host pin made from the first SHA256SUMS would then refuse the new bytes (fails closed, so the cost is availability). Fix: require TARGETS (or default to aarch64-apple-darwin) in --add mode, and compare git rev-parse HEAD with the release's targetCommitish before building.
- **hunter-supply**: scripts/release.sh --publish (line 101): if tag v$VERSION already exists, gh release create attaches to the existing tag and ignores --target, so the notes' 'commit $COMMIT' and the binaries could differ from the tag's commit. Fix: fail when git ls-remote --tags finds the tag, or when the tag's commit differs from HEAD.
- **hunter-supply**: scripts/release.sh line 90 hashes every dist/vault-$VERSION-*.tar.gz, including stale archives from earlier runs this run did not build or upload, so SHA256SUMS can list assets that do not exist on the release. Fix: hash only ${BUILT[@]}.
- **hunter-supply**: The release's clean-tree check (release.sh:31) and build.rs's dirty flag use --untracked-files=no, so an untracked build input such as a .cargo/config.toml in the checkout (rustflags, linker, source replacement) is not flagged; the toolchain (no rust-toolchain.toml), cargo-zigbuild and zig are unpinned. Same-principal only. Consider pinning the toolchain and refusing untracked files under .cargo/.
- **hunter-supply**: Manual installs (README.md:94-98, docs/releasing.md 'Installing from a release') check SHA256SUMS from the same GitHub release, with no signature, and the snippet's lines are not chained with &&, so pasting them continues to tar and install after a failed check. Consider signing SHA256SUMS (minisign or cosign) and chaining the install steps; the host's automated path already has an independent pin.
